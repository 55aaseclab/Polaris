# 客户分层分析

这份说明记录的是 `2026-06-30` 的市场判断。

这里不按地域拆分产品。
这里按客户类型、采购方式和真实运行需求来拆分市场。

## 市场框架

客户买的并不是一个抽象的 “agent”。
客户买的是下面四类结果之一：

- 让个人写代码更快
- 让团队在共享规则和上下文下提升产出
- 让 agent 在受治理的研发环境里安全执行
- 让工具、知识库和审批流程形成更广泛的自动化

不同结果，会导向不同候选产品清单。
这才是看这个市场的正确方式。

## 客户类型一：个人开发者

这一类客户首先要的是速度。
他们往往可以不经过正式平台决策，直接采用一个工具。

他们通常关心：

- 代码生成和修改质量是否足够强
- 上手成本是否足够低
- IDE 或 CLI 体验是否顺手
- 月度成本是否可以接受

他们可能评估的产品：

- Cursor
- GitHub Copilot
- Claude Code
- Codex CLI 以及相关 coding agents
- Windsurf
- Continue 这类自配置方案

他们购买的原因：

- 需要立刻看到生产力提升
- 不想等待基础设施准备完成
- 只要工具好用，通常能接受较弱的治理能力

这一类客户对 Polaris 不友好的地方：

- 采购是典型自下而上的
- 环境治理不是第一痛点
- 用户拿它比较的对象是一个顺滑的 assistant，不是基础设施控制层

## 客户类型二：小型研发团队

这一类客户通常是工程经理、技术负责人或创业团队负责人。
他们仍然看重速度，但已经开始需要团队范围内的一致性。

他们通常关心：

- 团队共享规则和提示词
- 对代码仓库上下文的理解能力
- seat 和 usage 成本是否可控
- 管理能力是否足够轻量
- 新成员 onboarding 是否足够快

他们可能评估的产品：

- Cursor Teams
- GitHub Copilot Business 或 Enterprise
- Sourcegraph Cody
- Continue 加内部模型或检索配置
- 围绕 Claude Code 或 Codex 做的轻量内部封装

他们购买的原因：

- 希望团队整体效率提升
- 希望减少工具和提示词漂移
- 希望 onboarding 不再依赖手工环境准备

这一层仍然存在的缺口：

- 治理能力通常偏浅
- 使用扩大后，成本很容易变得不可预测
- 工具行为容易受本地机器状态影响
- 共享凭证和共享算力很快会变乱

## 客户类型三：AI 应用构建团队

这一类客户通常是平台 PM、自动化团队或创新团队。
他们想要 agent，但不只想要 coding agent。

他们通常关心：

- 工作流编排能力
- 知识库集成能力
- 审批、tool calling 和流程控制
- 能否快速做出 PoC
- 连接器覆盖是否足够广

他们可能评估的产品：

- Dify
- LangGraph Platform
- Flowise
- 带 AI 扩展的 n8n
- Coze
- 各大云厂商的 agent studio 类产品

他们购买的原因：

- 希望业务工作流尽快上线
- 希望低代码和代码混合编排
- 很多时候，他们对连接器广度的需求高于 coding 深度

这一类与 Polaris 只部分重叠：

- 这类产品首先是 AI 应用构建平台
- 它们在研发工作空间 ownership 和 isolation 上通常较弱
- 它们通常不解决共享基础设施上的受治理代码执行问题

## 客户类型四：企业平台团队与安全团队

这一类客户掌握最难拿下的预算。
他们对控制、审计、上线安全和规模化负责。

他们通常关心：

- 身份与权限边界
- workspace 隔离
- 审计链路
- 网络与凭证控制
- 可重复的 onboarding 和 offboarding
- 面向多团队的策略执行

他们可能评估的产品：

- Coder
- Gitpod Enterprise
- 带 agent 与交付控制能力的 Harness
- AWS Bedrock AgentCore 及其相邻运行时控制层
- GitLab Duo Enterprise 及其平台侧能力
- 基于 Kubernetes、VM 或容器后端自建的平台

他们购买的原因：

- 他们需要的是平台级答案，不是单用户工具
- 他们必须在大规模 rollout 前治理外部 agent
- 他们需要一个可覆盖多仓库、多用户的统一运行模型

当前选项仍有空间的地方：

- 有些产品开发者体验强，但治理深度不够
- 有些产品通用 agent runtime 强，但不够贴近 coding workflow
- 有些产品基础设施能力强，但很难快速向开发团队证明业务价值

## 客户类型五：交付团队、外包团队与共享实验室

这一类客户会让很多用户跑在共享机器或受控环境上。
他们最关心租户边界和环境复用效率。

他们通常关心：

- 客户、项目或学员之间必须严格隔离
- 每个用户的初始化时间要足够短
- 凭证必须受控
- 项目状态要持久，但不能跨用户泄漏
- 人员轮换时，handover 要能延续

他们可能评估的产品：

- Coder
- Gitpod
- 内部 VDI 或远程工作空间方案
- 基于容器的培训或实验环境平台
- 围绕 CLI agents 组装的自定义 harness

他们购买的原因：

- 他们需要一个可复用的环境平面
- 他们不能接受跨用户状态泄漏
- 他们的人力轮换频率通常高于标准产品研发团队

这一类客户对 Polaris 很重要，因为：

- 共享基础设施本来就是第一优先级需求
- 用户 ownership 和 credential switch 是日常运行需求
- handover 是产品价值的一部分，不是后续补充能力

## 从客户视角看，市场会收敛成哪几类选择

跨这些客户类型，市场大致会收敛成三类实际选择。

### 选择一：assistant-first 产品

例子：

- Cursor
- GitHub Copilot
- Claude Code
- Codex

客户价值：

- 最快看到生产力结果
- 对个人用户最有吸引力

客户顾虑：

- 对共享环境的控制面较弱
- 治理和成本控制通常来得更晚

### 选择二：workflow 与应用构建平台

例子：

- Dify
- LangGraph Platform
- Flowise
- n8n

客户价值：

- 自动化覆盖范围广
- 适合快速做出 PoC

客户顾虑：

- 不是为受治理的软件工程执行场景设计的
- 在 workspace lifecycle 和 isolation 上通常不够强

### 选择三：受治理的工程平台

例子：

- Coder
- Gitpod Enterprise
- Harness
- 带企业控制能力的云端 agent runtime 平台

客户价值：

- 能提供身份、策略、审计和环境控制
- 更适合大规模 rollout 和受监管场景

客户顾虑：

- 采用动作更重
- 自下而上的吸引力弱于 assistant-first 工具
- 价值必须通过运行结果证明，而不是靠 demo 体验证明

## Polaris 的产品定位

Polaris 不应该把自己定位成又一个通用 agent builder。
它也不应该只把自己定位成一个 IDE assistant。

更清晰的定位应该是：

- 主定位：`面向工程团队的 coding agent 控制面`
- 副说明：`提供 workspace 隔离、凭证切换、运行治理和交接连续性`

这个定位重要，是因为它正好落在 assistant-first 工具和通用 agent
平台之间的空白带上。

从客户视角看，Polaris 解决的是一组仍然供给不足的能力组合：

- 可用的 workspace onboarding
- 清晰的 per-user ownership 边界
- 不重建环境即可完成 live credential switching
- 共享基础设施上的隔离能力
- 持久化的 runtime state
- 成员离开和交接过程中的连续性

## Polaris 的目标客户

Polaris 近期最合适的客户，不是所有开发者。
而是那些真实受到运行约束的团队。

最强的首批目标客户包括：

- 需要给很多工程师启用外部 coding agents 的平台团队
- 使用共享算力且要求严格 workspace 边界的组织
- 人员经常跨项目轮换的交付团队
- 需要用户自有凭证，同时又要求集中控制的团队

这些客户已经感受到 Polaris 解决的问题。
他们不需要再被教育“治理问题是否存在”。

## Polaris 的差异化

从客户视角看，Polaris 应该重点强调五件事。

### 1. 共享基础设施，但不共享状态泄漏

很多产品默认每个用户都有自己的私有本地机器。
Polaris 应该直接强调受控共享基础设施和清晰隔离。

### 2. 用户 ownership 与运行时控制可以同时成立

客户需要用户拥有自己的身份和凭证。
运营者又需要控制这些凭证何时、如何被激活。
Polaris 在这里有明确叙事。

### 3. 快速把新用户带到可用 workspace

第一个成功指标不是抽象治理。
而是新用户能否快速进入一个真正可用的环境。

### 4. 不重建 workspace，也能治理外部 agent

客户会混用多个 coding agent。
他们不希望每个工具都强迫自己接受一套新的环境模型。

### 5. 把 handover 当成产品能力，而不是附属流程

很多工具只做到执行这一步。
Polaris 应该把 handover、保留上下文和团队连续性当成核心价值。

## Polaris 不该正面竞争的方向

Polaris 不应该试图在下面这些维度正面取胜：

- 最强的原始模型输出
- 最炫的 IDE 原生编辑闭环
- 最广的低代码 workflow builder
- 最通用的云端 agent runtime 广度

这些赛道已经很拥挤，而且产品经济模型不同。

## 建议的产品陈述

更清晰的产品陈述应该是：

- 主定位：`面向工程团队的 coding agent 控制面`
- 能力说明：`提供 workspace 隔离、凭证切换、运行治理和交接连续性`

换成更直接的客户语言：

`Polaris 让工程团队可以在共享环境中使用外部 coding agents，`
`同时保持对 workspace、凭证、运行边界和交接过程的控制。`

## 建议的市场切入点

最好的切入方式不是“买我们的 agent 平台”。
更好的切入方式是一个明确的工程运营问题。

比较好的首批切入口：

- 标准化共享研发环境的 onboarding
- 在共享算力上治理外部 coding agents
- 把用户凭证和 workspace 镜像解耦
- 在成员轮换时保留项目上下文

这些切入口都直接对应 Polaris 当前的能力强项。

## 总结

不同客户看到的不是同一个市场。
他们会根据自己最先感受到的问题来列候选产品。

这也是为什么 Polaris 应该围绕受治理的工程执行来定位，
而不是围绕通用 agent 来定位。

最清晰的类别是：

`面向工程团队的 coding agent 控制面`

最清晰的买方是：

`那些必须让 coding agents 在真实运行约束下工作的团队`
