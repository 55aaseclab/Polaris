# 客户进入策略与路线图

## 商业化假设

Polaris 的销售单位是一条真实业务流程及其持续运行结果。
因此销售、实施和产品验证必须围绕同一条流程展开：

```text
发现流程 -> 量化基线 -> 建立模板 -> 小范围运行
-> 人工复核闭环 -> 比较结果 -> 复制到相邻流程
```

## 首个切入口

优先选择以下特征的团队：

- 一条流程每周重复处理，且处理量稳定
- 目前由 3 到 20 人协作
- 已经存在 SOP、表格或检查清单
- 有明确的退回、审批或异常成本
- 负责人愿意提供脱敏样本和试点时间

首个切入口不应以“模型能力最强”作为主卖点。
应以“让一条现有流程在两到四周内稳定运行”为承诺边界。

## 试点阶段

### 阶段 0：确认流程

输出：

- 一页流程图
- 输入和结果样本
- 角色与权限表
- 正常、异常和人工复核路径
- 现有处理时长、返工率和失败原因

没有这些材料，不进入产品定制。

### 阶段 1：单流程试点

范围：

- 只选择一条主流程
- 只接入必要的数据源和外部系统
- 保留人工确认和原有结果交付
- 为每个工作单元保留运行记录

退出条件：

- 一线人员能够独立完成处理
- 失败任务可以被定位并恢复
- 业务负责人确认输出质量达到约定标准

### 阶段 2：稳定运营

补齐：

- 流程版本和变更审批
- 超时、失败和异常队列
- 角色替换和交接
- 运行指标和定期复盘
- 凭证、数据和外部调用的权限边界

退出条件：

- 流程负责人可以维护日常规则
- 新处理人经过短培训即可接手
- 业务团队可以解释异常，而不是依赖开发人员排查

### 阶段 3：复制

复制顺序：

1. 同一团队的相邻流程
2. 同一组织的相同流程
3. 相同角色和相同数据形态的外部客户

复制的前提是流程模板、验收指标和实施清单可复用。
不能把每个客户都变成一次性项目。

## 包装方式

| 包装 | 适用情况 | 计费逻辑 |
| --- | --- | --- |
| 单流程试点 | 验证一个流程的价值 | 固定实施费或短期项目费 |
| 团队工作台 | 多人持续处理同一类工作 | 平台费加席位费 |
| 多流程运营 | 一个团队管理多条流程 | 平台费加执行量或工作区费 |
| 企业部署 | 有数据、权限和审计要求 | 企业合同、支持和部署费 |

模型调用和外部服务成本应单独可见。
客户买的是业务处理结果和运行控制，不是不可解释的 token 包。

## 路线图

### 现在：证明单流程闭环

- 稳定执行和状态持久化
- 卡片式工作台和人工任务队列
- 输入、输出、异常和运行记录
- [Polaris DSL](/polaris/workflow) 版本化和基础重试
- 权限、凭证和外部调用边界

### 下一阶段：证明团队运营

- 流程模板与发布流程
- 超时升级、批量处理和定时任务
- 角色替换、交接和结果归档
- 业务指标、失败原因和成本视图
- 常见文档、表格和内部系统连接器

### 再下一阶段：证明组织复制

- 多团队和多工作区隔离
- 策略中心与审计导出
- 模板复用和版本回放
- 流程质量评估与灰度发布
- 跨团队容量和资源治理

## 明确不做

- 先做一个面向所有人的通用聊天产品
- 先追求最大的模型或连接器数量
- 用复杂编排掩盖没有业务负责人和验收标准
- 在单条流程尚未稳定前扩展成行业 ERP 替代品
- 把个人 coding agent 或共享开发环境作为主销售叙事

## 销售叙事

对业务负责人：

> 把每天重复的业务处理做成可复用流程，让执行、复核、异常和交接都有
> 稳定记录。

对 IT 和安全负责人：

> 在不牺牲人工责任边界的前提下，把业务流程、数据访问和外部调用放进
> 可治理的执行环境。

对一线处理人员：

> 打开工作单元就知道要处理什么、缺什么、下一步是谁负责，以及怎样把
> 结果交付出去。
