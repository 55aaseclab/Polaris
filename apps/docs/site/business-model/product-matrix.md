# 业务流程执行模型

## 产品不是一个空白画布

Polaris 的最小销售单位不是一个 agent，也不是一个页面。
它是一条能够被团队反复执行的业务流程。

一条流程必须明确：

- 什么事件或请求触发处理
- 需要哪些输入和资料
- 哪些步骤可以自动执行
- 哪些节点必须由人判断
- 哪些情况进入异常、补料或审批
- 什么结果算完成
- 谁可以查看、修改、复核和交接

## 一条稳定流程的结构

```text
受理 -> 校验 -> 处理 -> 人工复核 -> 审批/补料 -> 交付 -> 归档
             \-> 异常处理 -> 重试/转人工 -/
```

每个节点都应有输入、输出、责任人、状态和失败路径。
没有失败路径的 happy path 只能算演示，不能算稳定业务流程。

## 核心对象

| 对象 | 作用 | 业务人员看到的内容 |
| --- | --- | --- |
| 流程模板 | 定义可复用的步骤和规则 | 这类请求应该怎样处理 |
| 工作单元 | 一次具体的业务处理 | 当前请求、资料和负责人 |
| 运行记录 | 记录每个节点的状态和结果 | 做到哪一步、为什么停下 |
| 人工任务 | 把判断交给指定角色 | 待复核、待补料或待审批 |
| 结果包 | 交付最终材料和结论 | 可发送、归档或进入下一系统 |
| 版本 | 管理规则和流程变化 | 本次处理使用了哪一版 |

## 自动化与人工边界

| 类型 | 适合自动化 | 必须保留人工控制 |
| --- | --- | --- |
| 输入处理 | 分类、抽取、格式统一 | 资料缺失时要求补充 |
| 规则检查 | 字段完整性、金额和格式校验 | 边界案例和规则冲突 |
| 内容生成 | 摘要、草稿、候选回复 | 对外发送和责任确认 |
| 外部调用 | 查询、同步、创建草稿 | 有副作用的提交和付款 |
| 结果归档 | 命名、标签、关联记录 | 归档范围和保留期限 |

原则是：自动化负责减少重复操作，人工负责承担业务判断和责任。
把人工节点隐藏在 agent 内部，会降低信任，也会让失败无法处理。

## 稳定运行的五个控制点

1. **状态明确**：待处理、处理中、待复核、待补料、已完成和失败要可区分。
2. **责任明确**：每个人工节点都有角色、负责人和接手规则。
3. **失败可恢复**：网络失败、资料缺失和规则拒绝不应让整单丢失。
4. **结果可解释**：输出应关联输入、规则版本和关键中间结果。
5. **变更可回溯**：流程变更先版本化，再发布、观察和回滚。

## 能力矩阵

| 能力层 | 首批必须具备 | 后续增强 |
| --- | --- | --- |
| 流程定义 | DSL、节点、分支、输入输出 | 模板市场、可视化编辑 |
| 执行 | 稳定调度、状态持久化、重试 | 并发策略、批处理和定时运行 |
| 人工协作 | 队列、指派、复核、审批 | 代理规则、超时升级和轮班 |
| 数据处理 | 文件、结构化字段、结果包 | 更多连接器和行业数据适配 |
| 治理 | 身份、权限、审计、凭证边界 | 策略中心、合规报表 |
| 运营 | 失败查看、恢复、版本回滚 | 质量分析、容量预测和成本优化 |

优先顺序是执行可靠性、人工闭环和可追踪性。
连接器数量、模型数量和界面装饰不应先于这些基础能力。

## 业务指标

试点必须同时记录业务结果和运行质量：

| 指标 | 定义 |
| --- | --- |
| 完成率 | 在约定时限内成功交付的工作单元比例 |
| 首次通过率 | 无人工退回或补料的比例 |
| 平均处理时长 | 从受理到交付的实际耗时 |
| 人工触达率 | 进入人工任务的比例 |
| 恢复成功率 | 失败后通过重试或补料完成的比例 |
| 交接耗时 | 负责人变更后恢复处理所需时间 |
| 结果返工率 | 交付后被退回或重新处理的比例 |

模型调用次数、token 数量和页面访问量只能作为成本或运营指标，
不能单独作为业务价值证明。
