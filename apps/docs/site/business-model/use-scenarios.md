# 业务场景模板

场景不是功能清单，而是可验证的业务流程假设。
每个场景都必须有明确的输入、步骤、人工节点、结果和衡量方式。

## 场景筛选标准

优先选择同时满足以下条件的流程：

1. 每周重复发生，且处理量可以估计
2. 处理步骤可以描述，至少有一个稳定的最小闭环
3. 输出会被客户、同事或下游系统使用
4. 失败、退回、审批或补料会造成真实成本
5. 有业务负责人可以提供样本并验收

## 场景卡片

### S01 客服工单分流与回复

**目标：** 让一线团队用统一规则处理高频请求，把复杂问题升级给正确
的负责人。

**最小流程：**

```text
导入工单 -> 提取客户与问题 -> 分类和优先级 -> 生成回复草稿
-> 一线复核 -> 发送或升级 -> 归档
```

**验收：**

- 分类结果有理由和引用的原始信息
- 回复发送前必须经过指定角色确认
- 升级后保留完整上下文，不要求客户重复描述

### S02 发票和付款前处理

**目标：** 减少财务人员在发票、采购单和合同之间重复核对的时间。

**最小流程：**

```text
接收材料 -> 抽取字段 -> 关联采购单 -> 规则校验
-> 异常复核 -> 形成付款建议 -> 归档
```

**验收：**

- 缺资料和金额不一致进入补料或异常队列
- 系统只生成付款建议，不绕过最终审批
- 每个结论都能回到源文件和规则版本

### S03 合同初审与条款核验

**目标：** 把标准合同的初步检查交给流程，把高风险判断留给法务。

**最小流程：**

```text
上传合同 -> 识别版本和主体 -> 检查条款 -> 标记风险
-> 法务复核 -> 输出修改建议 -> 归档
```

**验收：**

- 风险项必须关联原文位置
- 法务可以逐项接受、修改或驳回建议
- 输出明确标注为初审结果，不冒充最终法律意见

### S04 交付需求受理与分派

**目标：** 让客户需求从受理到负责人的分派有统一入口和可追踪状态。

**最小流程：**

```text
受理请求 -> 检查项目上下文 -> 识别范围与优先级
-> 交付负责人确认 -> 建立任务 -> 通知相关人
```

**验收：**

- 需求不完整时进入补料，而不是直接创建错误任务
- 负责人变更不会丢失上下文和历史判断
- 超时和阻塞状态有升级路径

### S05 售后故障受理与升级

**目标：** 缩短故障定位和升级时间，同时保留对客户承诺的证据。

**最小流程：**

```text
接收故障 -> 收集日志 -> 初步分类 -> 建议处理步骤
-> 工程师复核 -> 修复或升级 -> 回告客户 -> 关闭
```

**验收：**

- 严重度、影响范围和升级依据清晰
- 自动建议不能直接执行破坏性操作
- 关闭前必须记录结果和客户确认

## 场景交付模板

每个试点只选择一条主流程，并补齐以下内容：

| 项目 | 必须回答 |
| --- | --- |
| 起点 | 什么事件创建一个工作单元 |
| 输入 | 需要哪些字段、文件和权限 |
| 正常路径 | 最短可完成路径是什么 |
| 人工节点 | 谁在什么条件下做什么决定 |
| 异常路径 | 缺料、拒绝、超时和调用失败如何处理 |
| 终点 | 哪些条件下算完成，结果交给谁 |
| 指标 | 用什么基线比较效率和质量 |
| 责任 | 谁维护流程，谁对结果负责 |

## 不应作为首批场景的项目

- 只有“做一个 AI 助手”的抽象目标
- 没有重复量，无法建立基线的创新探索
- 需要一次性重建整个核心业务系统
- 只追求自动生成，不允许人工复核和责任确认
