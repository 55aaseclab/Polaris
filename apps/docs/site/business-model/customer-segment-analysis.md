# 稳定业务流程的业务处理团队

## 一句话定义

目标客户是：**每天重复处理一类业务请求，并且需要多人按同一规则
协作、复核、审批和交付结果的团队**。

他们的痛点不是“不会使用 AI”，而是业务处理无法稳定复制：

- 输入格式不统一，前置检查靠经验
- 处理步骤散落在表格、邮件、聊天和内部系统里
- 关键判断依赖少数熟手
- 异常发生后只能重新开始
- 负责人离岗后，其他人找不到上下文
- 管理者无法回答处理到哪一步、谁做了什么、为什么这样处理

## ICP

### 必备条件

一个客户至少应满足以下四项中的三项：

| 条件 | 识别信号 |
| --- | --- |
| 高频重复 | 每天或每周处理大量相似请求 |
| 明确步骤 | 能说出受理、处理、复核和交付的顺序 |
| 人机协作 | 自动处理后仍需要人工判断、审批或补料 |
| 结果有责任 | 错误会带来客户、财务、合规或交付影响 |

### 优先客户

| 客户团队 | 典型流程 | 第一买方 |
| --- | --- | --- |
| 客服与运营 | 工单分流、资料核验、客户回复 | 运营负责人 |
| 财务与采购 | 发票处理、对账、付款前复核 | 财务负责人 |
| 法务与合规 | 合同初审、条款检查、材料归档 | 法务或合规负责人 |
| 交付与售后 | 需求受理、项目交接、故障处理 | 交付负责人 |
| 研究与知识支持 | 资料整理、报告初稿、证据核验 | 研究负责人 |
| 企业内部服务 | 入职、权限申请、资产和账号变更 | 共享服务负责人 |

工程团队、平台团队和共享实验室是相邻客户。
只有当它们需要稳定执行上述业务流程时，才属于首要销售对象。

## 购买委员会

| 角色 | 关心的问题 | 需要看到的证据 |
| --- | --- | --- |
| 业务负责人 | 处理量、时效和质量是否改善 | 前后流程对比和结果指标 |
| 一线处理人 | 是否减少重复搬运，异常是否好处理 | 实际工作台和失败恢复演示 |
| 流程设计者 | 规则变化是否容易维护 | [Polaris DSL](/polaris/workflow) 变更、版本和发布记录 |
| IT / 安全 | 权限、数据、凭证和外部调用是否可控 | 权限矩阵、审计记录和隔离边界 |
| 财务负责人 | 成本是否随处理量可预测 | 执行量、席位和资源成本模型 |

成交的必要条件不是单次 demo 成功，而是业务负责人愿意把一条真实流程
交给系统持续运行。

## 业务处理成熟度

| 阶段 | 现状 | Polaris 的切入方式 |
| --- | --- | --- |
| L0 临时处理 | 依赖个人经验和聊天记录 | 先梳理流程和结果定义 |
| L1 有模板 | 有表格或 SOP，但执行分散 | 把步骤、字段和责任人固化 |
| L2 可协作 | 有多人接力和人工复核 | 引入状态、队列、审批和交接 |
| L3 可度量 | 能统计量、时效和失败原因 | 建立运行指标和异常闭环 |
| L4 可持续优化 | 按数据持续调整规则 | 版本化 [Polaris DSL](/polaris/workflow)，灰度和回放验证 |

首批客户应集中在 L1 到 L3。
L0 需要过多流程咨询，L4 则通常要求更深的企业数据和治理集成。

## 资格判断

### 适合进入试点

- 可以指定一条真实且重复的流程
- 可以提供一组脱敏历史样本
- 可以指定流程负责人和一线试用者
- 可以定义完成、退回、失败和超时的结果
- 愿意在两到四周内比较基线与试点数据

### 暂不进入试点

- 只想做一个开放式聊天机器人
- 只有一次性的内容生成需求
- 没有流程负责人，也没有验收标准
- 所有输入和规则都不稳定，无法形成最小流程
- 只要求模型回答正确，不接受运行记录和人工复核

## Polaris 与替代方案

| 替代方案 | 能解决什么 | 仍然缺什么 |
| --- | --- | --- |
| 表格、邮件和聊天 | 灵活，启动成本低 | 状态、责任、版本和异常不可控 |
| 人工外包 | 能快速扩充处理量 | 规则沉淀、质量一致性和交接较弱 |
| 脚本拼接 | 对固定输入效率高 | 人工节点、失败恢复和业务可见性不足 |
| 通用自动化平台 | 连接器和触发器丰富 | 复杂业务处理容易变成难维护的黑盒 |
| 通用 AI 对话 | 适合探索和一次性任务 | 不能天然保证步骤、审批和结果交付 |
| Polaris | 把流程、执行、复核和记录放在一起 | 需要先明确业务流程和责任边界 |

## 产品边界

Polaris 当前不以以下客户为主：

- 只追求个人写代码速度的用户
- 只需要通用聊天和内容生成的个人用户
- 只想搭建模型实验，不承担真实业务结果的技术团队
- 需要完整 ERP、CRM 或行业核心系统替代的组织

这些需求可以成为集成对象或后续扩展，但不能取代稳定业务流程团队这一
主定位。
