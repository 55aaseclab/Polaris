# Marketplace Monitor Pack（0.5.0）

Status: planned first commercial workflow for Polaris **0.5.0**.

## 用户结果

普通用户无需编写 DSL 或部署采集程序，只需保存筛选条件。Polaris 按计划检查
闲鱼新商品，对结果去重并判断相关性，再把真正新增且符合条件的商品通知用户。

## 输入

| 字段 | 说明 |
| --- | --- |
| `keywords` | 必须出现的商品关键词 |
| `priceRange` | 最低价与最高价 |
| `locations` | 可选地区范围 |
| `excludedTerms` | 排除词、型号或卖家描述 |
| `condition` | 可接受的成色或商品状态 |
| `schedule` | 平台允许范围内的检查频率 |
| `channels` | 小程序、站内或 Webhook 通知 |

## 执行流程

```text
计划触发 -> 查询来源 -> 规范化 -> 去重 -> 规则过滤
-> AI 相关性判断 -> 建立事件 -> 幂等通知 -> 记录回执
```

AI 只负责处理规则难以表达的相关性、描述质量和推荐理由。价格区间、排除词、
去重和通知幂等必须由确定性逻辑处理，避免模型波动破坏稳定性和成本控制。

## 输出

每个匹配事件至少包含：

- 商品标题、价格、地区和原始链接。
- 来源商品 ID、首次发现时间和来源更新时间。
- 命中的规则、AI 推荐理由和置信信息。
- 工作流版本、订阅 ID 和去重键。
- 通知渠道、投递状态、重试次数和最终回执。

## API 示例

```http
POST /v1/workflows/xianyu-monitor/subscriptions
GET  /v1/subscriptions/{subscriptionId}/events
```

API 与小程序、Web 使用同一个 workflow ID 和订阅资源，不建立 API 专用流程。

## 可靠性要求

- 来源超时、限流和会话失效要单独记录并采用有上限的退避重试。
- 增量游标与去重状态必须持久化，服务重启后继续运行。
- 重跑同一时间窗口不得重复产生已经确认的事件。
- 通知失败可重试；已经确认的投递不得重复发送。
- 来源结构变化时自动熔断，并允许在不丢失订阅的情况下升级适配器。

## 合规边界

- 只处理提供服务所需的数据，不建立无关的个人信息档案。
- 遵守目标平台条款、访问频率和公开数据边界。
- 不绕过验证码、反自动化控制、登录保护或账号限制。
- 在平台规则不允许自动访问时停止对应能力，并向用户说明状态。
- 原始链接和来源时间必须保留，AI 判断不能替代来源事实。

## 0.5.0 验收

1. 用户能从小程序或 Web 创建、暂停、恢复和取消监控。
2. 合成来源测试覆盖新增、更新、重复、删除和来源失败。
3. 规则过滤与 AI 筛选可独立观察，AI 失败不破坏确定性去重。
4. 一条商品最多生成一个有效新增事件和一次已确认通知。
5. API 客户能查询同样的事件，并通过签名 Webhook 接收通知。
