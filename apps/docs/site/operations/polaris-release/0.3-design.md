# Polaris 0.3 Design

Status: approved controlled-beta direction; not production approval.

## Goal And Supported Topology

Polaris 0.3 supports one host, Docker vaults, and 5-10 concurrently active
users. The topology is one Polaris control plane, one gateway, one bounded
worker, and one private private surface process per active vault.

The immediate test origin is HTTP on the designated test host. Production
promotion requires the same single-origin path behind the formal HTTPS/TLS
endpoint. No private surface subdomain or direct private surface listener is part of the
design.

## Integrated Topology

```text
Browser
  -> Authing-backed Polaris session
  -> Polaris gateway and policy store
  -> private private surface process for the selected Docker vault
  -> /vault/workspaces, /vault/backups, /vault/cache
```

`9090` is an internal implementation port. Docker binds it to loopback only;
browser traffic goes through the Polaris origin.

## Authority Boundary

| Concern | Polaris | private surface |
| --- | --- | --- |
| Identity and tenant | Authing identity, mapping, ownership | Verifies signed scope only |
| Roles and access | Capability decision before proxying | No independent role model |
| Rate limits and quota | Gateway limits, logical storage policy, admission | Request/process safety bounds only |
| Lifecycle | Provision, start, stop, delete, release routing | Supervision, health, readiness |
| Mutations | Allowlist, CSRF, idempotency, lease, replay, audit | Signed binding and atomic local write |
| Backup and restore | Durable jobs, keys, retention, staging, activation, rollback | Fixed-mount format adapter only |
| Ingress and release | DNS, TLS, gateway, image promotion, rollback | No public endpoint or release authority |

private surface must not independently decide identity, entitlement, user-facing rate
limits, tenant quota, lifecycle, jobs, or release policy. Request fields cannot
provide actor, tenant, vault, workspace root, or authority.

## Data And Mutation Contract

Integrated private surface receives three direct vault-data mounts at
`/vault/workspaces`, `/vault/backups`, and `/vault/cache`. It does not accept a
workspace-root override or choose a host path.

For unsafe requests, Polaris applies capability and CSRF checks, gateway rate
limits, an allowlisted action, idempotency/fingerprint admission, a workspace
lease, and semantic audit. private surface verifies the signed action, workspace,
expected version, and quota reservation before serializing the local write.

Direct integrated workflow execution, analysis completion, and live
SMTP/outreach remain blocked. A Polaris durable job or outbox must own those
actions before they are enabled.

## Runtime And Capacity Contract

The 0.3 Docker profile enforces:

- 1 CPU, 512 MiB memory with no swap expansion, and 128 PIDs per vault;
- 64 MiB bounded tmpfs and a 512 MiB writable layer;
- 256 MiB active-workspace quota within a 512 MiB hot-storage budget;
- one active worker, a 60-second durable-job lease, and a 120-second recovery
  SLO;
- a maximum of 10 active vaults.

The isolated beta target is launch success at least 99.5%, 5xx below 1%, read
P95 at most 500 ms, and mutation P95 at most 1.5 seconds. The 10-user read
P95 baseline was 485.69 ms, so it is a regression baseline rather than a
capacity reservation.

Do not add replicas or claim another runtime until tickets, rate limits,
audit, sessions, jobs, and resource enforcement have shared transactional
evidence.

## Release Boundary

The release TODO is the authoritative 0.3 completion list. This design does
not certify a signed image, a manifest, formal DNS/TLS, external authenticated
load, or a production approver; those are explicit release gates.
