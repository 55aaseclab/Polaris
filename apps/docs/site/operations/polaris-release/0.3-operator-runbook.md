# Polaris 0.3 Operator Runbook

Status: **test-host runbook**. This page is for the one-host, Docker-only
0.3.0 profile. It does not authorize formal production promotion. The current
candidate uses the designated HTTP test origin; formal HTTPS/TLS and signed
external promotion are deferred to 0.3.2.

## Safety Rules

- Keep private surface behind the Polaris `/g/` path. Never publish container
  port `9090` or point host Nginx at a raw Polaris Node port.
- Keep tenant data outside the application checkout. Never remove a tenant
  root, a backup key root, or a control database during troubleshooting.
- Do not restart both blue and green services together. Use the deployment or
  rollback script so the release lock and health gate remain in effect.
- Do not run a backup, restore, or migration by editing files directly. Use
  the Polaris durable job/API path and capture its job identifier.

## Variables

Set these for the deployed host. Values are operator-managed and must not be
committed or pasted into public evidence:

```bash
APP_DIR=/srv/polaris/app
ENV_FILE=/etc/polaris/polaris.env
ACTIVE_COLOR_FILE=/etc/polaris/active-color
UPSTREAM_FILE=/etc/nginx/snippets/polaris-gateway-upstream.conf
DATA_ROOT=/srv/polaris/data
COMPOSE_FILE="$APP_DIR/deploy/docker-compose.polaris-bluegreen.yml"
POLARIS_ORIGIN=http://m00e04c1b76c0.dyn.epfl.ch
```

Read the active color before checking logs or selecting a rollback target:

```bash
ACTIVE_COLOR="$(tr -d '[:space:]' < "$ACTIVE_COLOR_FILE")"
case "$ACTIVE_COLOR" in blue|green) ;; *) echo "invalid active color" >&2; exit 1 ;; esac
```

## Health And Traffic

Check the same origin that a browser uses. For a local check, use the active
host proxy; for an external check, use the configured Polaris origin:

```bash
curl -fsS "$POLARIS_ORIGIN/healthz"
curl -fsS "$POLARIS_ORIGIN/readyz"
curl -sS -D - "$POLARIS_ORIGIN/" -o /dev/null
sudo nginx -t
sudo systemctl is-active "polaris-server@${ACTIVE_COLOR}.service"
sudo docker compose -f "$COMPOSE_FILE" -p "polaris-${ACTIVE_COLOR}" --env-file "$ENV_FILE" ps
```

Expected root probe bodies are `status=ok` and `status=ready`. A `502` from
host Nginx means its configured internal proxy is absent or unhealthy; do not
work around it by exposing `18787`, `28787`, or `9090`. Inspect the inactive
stack and use the normal deployment path.

## Logs And Backup Status

Capture recent logs without copying cookies, assertions, request bodies, or
secret values into tickets:

```bash
sudo journalctl -u "polaris-server@${ACTIVE_COLOR}.service" -n 100 --no-pager
sudo docker compose -f "$COMPOSE_FILE" -p "polaris-${ACTIVE_COLOR}" --env-file "$ENV_FILE" logs --tail=100 nginx paseo-app
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

The durable job state is in `$DATA_ROOT/control/state/control.sqlite`. If the host
provides `sqlite3`, inspect counts and statuses only:

```bash
sudo sqlite3 "$DATA_ROOT/control/state/control.sqlite" \
  "SELECT kind,status,COUNT(*) FROM jobs GROUP BY kind,status ORDER BY kind,status;"
```

For a backup incident, record the tenant/vault/job identifiers, status,
attempt count, error code, and timestamps. Do not print `payload_json`, result
contents, assertions, or key material. Verify the backup key directory remains
private and that the encrypted copy is outside the hot workspace volume:

```bash
sudo stat -c '%A %U:%G %n' "$DATA_ROOT/control/backup-keys"
sudo df -h "$DATA_ROOT" /var/lib/docker
```

## Disk Pressure

Run these read-only checks before pruning anything:

```bash
df -h "$DATA_ROOT" /var/lib/docker
sudo docker system df
sudo du -sh "$DATA_ROOT" /var/lib/docker 2>/dev/null
```

Stop new vault admission and escalate when free space is falling toward the
operator's reserve. Only the installed, retention-bounded cleanup job may
remove stale `ttl.sh` runtime artifacts. Never use an unrestricted
`docker system prune` during an incident.

## Rollback

Rollback changes traffic to the previous healthy color and preserves tenant
roots. Confirm the target color has a healthy stack, then run from the deployed
application directory:

```bash
cd "$APP_DIR"
bash ./scripts/rollback-polaris.sh \
  "$ENV_FILE" \
  "$TARGET_COLOR" \
  "$ACTIVE_COLOR_FILE" \
  "$UPSTREAM_FILE"
```

Set `TARGET_COLOR` to the inactive color before running the command, for
example `TARGET_COLOR=green` when `ACTIVE_COLOR=blue`. It must be `blue` or
`green` and must not equal `ACTIVE_COLOR`.
After rollback, repeat the health, compose, and direct-port checks. Record the
previous and new active colors, manifest digests, smoke result, and reason.
Do not delete the failed color until evidence and logs are retained.

## Incident Stop Conditions

Stop the release and leave the profile **NO-GO** when any of these occurs:

- real Authing is unavailable or the origin is not the approved single origin;
- a private surface `9090` mapping is public or a direct route bypasses Polaris;
- tenant, vault, workspace, backup, or control-store ownership is ambiguous;
- a durable job is running without a lease, duplicate protection, or recoverable
  status;
- the local candidate manifest or rollback target is missing.

For 0.3.0 test-host releases, signature, provenance, SBOM, formal TLS/DNS,
and external-service promotion failures are recorded as 0.3.2 work rather
than bypassed through an alternate public route.

Record the command output privately, redact it before documentation, and keep
the release TODO checkbox empty when the evidence does not match the named
environment.
