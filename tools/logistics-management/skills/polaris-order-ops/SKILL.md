# Polaris 订单履约与单据工作流

版本：`v1.0`

当任务涉及订单流转、报价、报检、发货、开票资料、台账建立、对账归档或流程搭建时，使用本 skill。

本 skill 的目标不是伪造后台，而是先用可追溯、可归档的文档和台账，生成一套等价于后台核心结果的业务记录。

## 先读什么

1. 先读 `references/workflow.md`，确认当前处于哪个业务阶段。
2. 如有具体业务背景资料，再按需读取对应业务目录中的文档。
3. 如需输出单据骨架，优先使用 `assets/` 下的模板。

## 适用任务

- 梳理从接单到归档的执行顺序
- 在没有系统后台时建立手工订单台账
- 建立产品资料 folder、产品编号和产品卡，使订单与产品编号可对照
- 产品有图片时，必须把原图或截图归档到对应产品 folder，不只记录文字描述
- 生成报价单、PI（形式发票）、CI（商业发票）、报检单、收款记录、开票信息、发货记录、对账记录
- 检查一笔订单目前缺什么资料
- 把聊天记录、Excel、图片信息整理成结构化单据
- 给下一步执行列出最小必需输入项

## 核心原则

- 只围绕真实交易生成记录，不为不存在的交易生成单据。
- 发票只能基于真实成交、真实收款/应收关系和真实货物或服务内容整理开票信息。
- “后台结果”在本 skill 中指手工整理出的订单号、客户、商品、金额、收款、物流、开票和对账记录，不指伪造平台页面截图。
- 每一笔业务都要能串起来：`订单号 -> 报价 -> 报检 -> 收款 -> 发货 -> 开票 -> 对账 -> 归档`。
- 对缺失信息要明确标注 `待补充`，不要擅自编造。
- 客户可见文件必须只包含客户应看到的信息。报价单、PI、CI、报检单等对外文件不得暴露进价、利润、倍率、定价公式、内部推导过程、旧数据纠错、对话记录或“旧口径作废”等内部判断。
- 内部定价依据、成本核算、数据修正原因只能写入内部 `meta.json`、对账记录或内部备注，不得写入客户可见 PDF/HTML。
- 产品 `list_price` 不使用单一倍率。先计算内部成本 `purchase_price + packaging_price + labor_price`，再结合品类、用途、寓意、体量和心理价位确定市场标价。
- 货号 43 的 `389 CNY` 是强寓意挂坠的品牌锚点价，只能作为同类寓意款参考，不能反推所有产品价格。

## 定价与利润口径

- 单品基础成本：`base_cost = purchase_price + packaging_price + labor_price`。未知成本先标记 `待补充`；如必须估算，明确写明估算项。
- 市场标价：`list_price` 先参考 `base_cost`，再结合品类、用途、寓意、体量和心理价位确定。不要用一个产品的价格反推所有产品。
- 订单已知毛利：`known_gross_profit = customer_payable - sum(purchase_price + packaging_price + labor_price) * quantity`。
- 订单实际利润：`actual_profit = customer_payable - product_costs - actual_shipping_cost - payment_fee - other_loss`。
- 毛利率：`gross_margin = known_gross_profit / customer_payable`。金额为 0 或待确认时不要计算百分比。
- 缺物流或手续费时，可以给区间估算，例如 `已知毛利 - 150/200/250`，但必须说明这不是最终利润。
- 成本、毛利、利润、定价原因只写入内部 `meta.json`、对账记录或内部备注，不进入客户可见报价单、PI、CI、报检单。

## 标准执行顺序

1. 确认交易主体：
- 谁是销售方
- 谁是供货方
- 谁是付款方
- 谁是收货人

2. 建订单主记录：
- 确认已有订单号
- 在 `订单管理/<订单号>/meta.json` 维护订单主记录
- 在 `报价/`、`报检/`、`收款/`、`发货/`、`开票/`、`对账/`、`归档/`、`附件/` 子目录维护业务材料
- 上述每个业务子目录都维护独立 `meta.json`
- 记录客户、币种、商品、数量、单价、成交金额
- 在订单主记录中维护收款、发货、对账和归档状态
- 商品行优先写成 `产品编号 + 产品名称`
- 标记销售渠道来源，例如微信、邮件、线下、独立站人工录入

3. 生成报价单、PI 和 CI：
- PI 用于付款前或付款确认阶段，作为形式发票给客户确认
- CI 用于实际出货、清关或正式贸易单据整理
- PI 与 CI 的商品、数量、金额、币种要与真实订单保持一致
- 当前未确定内容要明确标注，不得伪造抬头、税号或贸易条款
- 报价单是客户可见文件，只展示商品、数量、币种、对客户报价、运费和客户应付总额。不要写进价、折扣推导、倍率、利润、内部备注、历史错误来源或任何对话痕迹。
- 报价前先确认产品 `pricing.markets.<market>.list_price`。若需重估，按成本、品类和心理价位确定，不要机械套用 43 号的品牌锚点价。
- 如需正式发送，优先输出 HTML 和 PDF

4. 建收款记录：
- 收款信息写入 `订单管理/<订单号>/收款/meta.json`
- 记录应收金额、实收金额、收款时间、收款方式、汇率口径
- 若未收款，标记为 `待收款`

5. 建发货记录：
- 发货流程状态和发货明细写入 `订单管理/<订单号>/发货/meta.json`
- 记录包裹件数、重量、物流商、渠道、运单号、发货时间、目的国
- 若跨境物流待确认，标记为 `待发货`

6. 建报检记录：
- 在发货前生成报检单或验货单
- 记录订单号、客户、目的国、商品明细、包装要求、外观检查、数量检查、配件检查、签字日期
- 若包装、标签或随货资料未确认，标记为 `待报检完成`

7. 建开票记录：
- 确认是否需要开发票
- 如需开票，记录抬头、税号、开票内容、金额、邮箱、开票状态
- 如暂不开票，标记为 `未申请开票`

8. 建对账与归档记录：
- 对账状态写入 `订单管理/<订单号>/对账/meta.json`
- 归档清单写入 `订单管理/<订单号>/归档/meta.json`
- 核对订单金额、收款金额、发票金额、物流费用、采购或供货结算金额
- 归档相关截图、聊天、报价、PI、CI、报检单、付款凭证、物流面单和发票文件位置
- 归档时记录报价、报检、收款凭证、发货材料、开票材料、对账材料的位置

## 输出规则

- 默认使用中文输出。
- 优先输出结构化表格或可直接复制的 Markdown 模板。
- 如果用户只给了零散信息，先整理成 `已知信息` 与 `待补充信息`。
- 如果用户要求“正规”，优先强调留痕、可追溯、真实一致，而不是形式上像后台。
- 如果用户要求“先做后台结果”，优先生成台账和业务单据，不直接生成税务发票成品。

## 缺失信息处理

- 缺客户名称：先用临时客户标识，但明确标记待替换。
- 缺商品明细：只建订单头，不建金额和开票内容细项。
- 当前版本默认不使用 `规格/款式` 字段；如后续需要标准化，放到报检单版本信息中处理。
- 缺产品图片：明确标记 `待补产品图`，不要假设图片已归档。
- 缺收款凭证：订单可建，但收款状态必须是 `待核实`。
- 缺物流单号：发货状态只能写 `待补充运单号`。
- 缺包装方案或验货结果：报检状态只能写 `待确认包装/待完成报检`。
- 缺开票资料：只能输出 `开票信息收集清单`，不能假定抬头和税号。
